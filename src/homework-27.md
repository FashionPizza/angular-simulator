Задача №1. Singleton или нет?
1 экземпляр. providedIn: 'root' регистрирует сервис в root injector, а он один на приложение. У обоих компонентов нет своих провайдеров, поэтому оба получают сервис из root injector. При первом запросе Angular создает экземпляр и кеширует его, при втором запросе возвращает кеш, поэтому id в ComponentA и ComponentB совпадут.

Задача №2. Локальный Provider
2 экземпляра. Провайдеры в декораторе компонента создают свой element injector у каждого экземпляра компонента. В шаблоне два элемента <app-child>, это два отдельных инжектора. Каждый компонент находит провайдер у себя и получает свой новый CounterService. Root injector тут вообще не участвует, root-экземпляр не создается.

Задача №3. Какой экземпляр получит компонент?
Родительский экземпляр, созданный в ParentComponent. Angular ищет снизу вверх: у ChildComponent своих провайдеров нет, поэтому он поднимается к ParentComponent, находит провайдер там и останавливается. Берется первый найденный провайдер, поэтому до root injector поиск не доходит.

Задача №4. useExisting
1 экземпляр. useExisting это алиас на другой токен, он ничего не создает. Запрос inject('LOGGER') раскрывается в поиск токена LoggerService, поэтому оба вызова резолвятся в один и тот же объект.

Задача №5. useFactory
При первом inject(). В момент объявления providers фабрика не выполняется, Angular только запоминает, как создать сервис. При первом inject() кеш пуст, вызывается фабрика, результат кешируется. Все следующие inject() берут значение из кеша.

Задача №6. Multi Provider
В value окажется массив из строк 'A' и 'B'. При multi: true токен хранит массив, каждая регистрация добавляет значение в массив в порядке объявления. inject(TOKEN) возвращает весь массив целиком.

Задача №7. Optional
Вернется null, ошибки не будет. Без optional неудачный поиск выбрасывает NullInjectorError, а с optional: true Angular вернет null, если провайдер не найден по всей цепочке. Проверять результат на null и решать, что делать дальше, должен сам разработчик.

Задача №8. Self
Ошибка NullInjectorError. self: true запрещает подниматься выше собственного element injector. Своих провайдеров у ChildComponent нет, поэтому поиск сразу проваливается. То, что сервис есть в root, не помогает, потому что до root injector поиск просто не доходит.

Задача №9. SkipSelf
Родительский экземпляр. skipSelf: true пропускает собственный инжектор компонента и начинает поиск с родителя. У ParentComponent есть локальный провайдер, он и будет найден первым, поиск на нем остановится. До root дело не дойдет, потому что skipSelf означает «начни с родителя», а не «возьми из root».

Задача №10. Нет регистрации
Ошибка NullInjectorError: No provider for ApiService! Angular проверит собственный инжектор, затем инжекторы родителей, потом root injector и в конце platform injector, но провайдера нигде нет. Без optional: true пустой результат недопустим, поэтому код с inject() упадет в момент выполнения.

Задача №11. Что произойдет?
1 экземпляр LoggerService. Оба запроса резолвятся через root injector. Первый inject() создает экземпляр и кеширует его, второй находит кеш и возвращает его. logger1 и logger2 это один и тот же объект.

Задача №12. Финал
Экземпляра два. Первый локальный, его создает HeaderComponent вместе с собой, у него свой провайдер. Второй root-экземпляр, его создаст root injector при первом запросе от DashboardComponent или UserCardComponent, потому что у них своих провайдеров нет.
Свой локальный. Поиск начинается с собственного element injector, провайдер найден сразу, поэтому до root injector поиск не доходит.
Root-экземпляр. У DashboardComponent своих провайдеров нет, поиск поднимается через AppComponent до root injector, где сервис зарегистрирован через providedIn: 'root'.
Тот же root-экземпляр, что и у DashboardComponent. У UserCardComponent и его предков провайдеров нет, поиск доходит до root injector и берет уже закешированный экземпляр.
Поиск идет снизу вверх. Сначала Angular проверит собственный инжектор UserCardComponent, потом инжектор DashboardComponent, потом инжектор AppComponent, после этого root injector и в самом конце platform injector. Если провайдер нигде не найден, будет NullInjectorError.

Задача №13.
Root injector ищет провайдер по токену A и находит его.
Экземпляра A в кеше еще нет, поэтому Angular создает new A() и кеширует его в root injector.
При конструировании A выполняется поле b = inject(B). Root injector ищет провайдер B, кеш пуст, создается new B() и кешируется.
При конструировании B выполняется поле c = inject(C). Точно так же создается и кешируется new C().
При конструировании C выполняется поле d = inject(D). Создается и кешируется new D().
При конструировании D выполняется поле logger = inject(LoggerService). Создается и кешируется new LoggerService().
Дальше цепочка собирается в обратном порядке. Экземпляр LoggerService нужен конструктору D, готовый D возвращается в C, готовый C возвращается в B, готовый B возвращается в A, и готовый A возвращается в то место, где был вызван inject(A).
Всего создается 5 объектов: A, B, C, D и LoggerService. Все они кешируются в root injector, поэтому повторный inject(A) вернет кеш без создания нового.

Задача №14.
До выполнения inject(UserService) в памяти 0 сервисов. providedIn: 'root' не создает сервис при старте приложения, root injector хранит только инструкцию, как создать сервис. Пока никто не сделал inject(), объектов нет.
После выполнения inject(UserService) появится 3 объекта: UserService, ApiService и LoggerService. Создание идет каскадом. inject(UserService) создает new UserService(). При его конструировании выполняется inject(ApiService), поэтому создается new ApiService(). При конструировании ApiService выполняется inject(LoggerService), поэтому создается new LoggerService(). Все три экземпляра кешируются в root injector. В памяти оказываются только те сервисы, которые реально нужны.

Задача №15.
ApiService. Зарегистрируем через providedIn: 'root'. Сервис выполняет HTTP-запросы для всего приложения, поэтому нужен один экземпляр на все приложение.
AuthService. Тоже providedIn: 'root'. Текущий пользователь один на приложение, и шапка, и гварды, и любые компоненты должны видеть одно и то же состояние.
CartService. Тоже providedIn: 'root'. Корзина общая: добавил товар на странице каталога, и бейдж в шапке, и страница корзины должны показать то же состояние.
ProductFilterService. Провайдеры роутинга. Провайдер на маршруте создается при входе на страницу и уничтожается при выходе, поэтому фильтры исчезают после ухода. Компонентные провайдеры тут не подойдут, потому что фильтры обычно шарятся между несколькими компонентами страницы, например между панелью фильтров и списком товаров.
NotificationService. providedIn: 'root'. Показывать уведомления может любой компонент из любого места, а окно уведомлений одно на приложение.
ThemeService. providedIn: 'root'. По условию все страницы используют одну тему, значит состояние темы должно быть глобальным.
DashboardStatisticsService. Провайдеры роутинга. Сервис нужен только на странице Dashboard и должен умирать при уходе с нее. Привязка к маршруту дает ровно такой жизненный цикл.
UserTableStateService. Провайдеры роутинга. Сортировка, текущая страница и фильтры нужны только внутри страницы пользователей, поэтому состояние изолируется на маршруте и очищается при уходе.
ModalService. providedIn: 'root'. Открыть модальное окно должен уметь любой компонент приложения, а метод isModalOpen() подразумевает одно общее состояние окон.
LoggerService. useFactory. Поведение зависит от окружения: в production логи уходят на сервер, в development пишутся в консоль. Фабрика проверяет isDevMode() и возвращает нужную реализацию.
AppConfig. InjectionToken вместе с useValue. Это статичные данные, а не логика: готовый объект внедряется через useValue, а типобезопасность обеспечивает InjectionToken с интерфейсом.
CurrencyFormatter. Тоже InjectionToken с useValue. Формат числа это статичное значение, а не поведение.
AnalyticsService. useFactory. Фабрика читает флаг из конфига. Если аналитика включена, возвращается настоящий сервис, если выключена, возвращается заглушка. Остальной код при этом спокойно делает inject() без проверок.
